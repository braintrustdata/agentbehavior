## Terminology

- **Agent Behavior** is this format.
- A **behavior spec** is one `.agents/behaviors/<name>/BEHAVIOR.md` file and its directory.
- A **behavior** is a recurring pattern of agent conduct.

The key words **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, and **MAY** in this document are to be interpreted as described in [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119).

## Directory structure

Behavior specs are stored under `.agents/behaviors/`. Each behavior spec is a directory with a `BEHAVIOR.md` file:

```text
.agents/behaviors/
└── behavior-name/
    ├── BEHAVIOR.md       # Required: metadata and behavior text
    ├── references/       # Optional: rationale, examples, background docs
    └── ...               # Optional additional files
```

The directory name is the behavior's stable identifier and MUST match the `name` field in `BEHAVIOR.md`.

## `BEHAVIOR.md` format

The canonical file name is `BEHAVIOR.md`. Clients MUST look for `BEHAVIOR.md` when discovering behavior specs and MAY accept case variants. Case variants are valid when accepted by a client, but portable behavior specs SHOULD use `BEHAVIOR.md`.

A `BEHAVIOR.md` file MUST contain YAML frontmatter followed by Markdown content.

### Frontmatter

| Field | Required | Constraints |
| --- | --- | --- |
| `name` | Yes | Max 64 characters. Lowercase letters, numbers, and hyphens only. MUST NOT start or end with a hyphen. MUST match the parent directory name. |
| `description` | Yes | Max 1024 characters. Non-empty. Describes the behavior and when it applies. |
| `format_version` | No | Positive integer. If omitted, clients MUST treat the behavior spec as format version `1`. |
| `license` | No | License name or reference to a bundled license file. |
| `metadata` | No | Key-value mapping for client-specific metadata. |

Clients MUST ignore unknown frontmatter fields for supported format versions.

**Minimal example:**

```markdown BEHAVIOR.md
---
name: behavior-name
description: Describe the recurring behavior and when it applies.
---

# Behavior name

Describe the behavior, including what evidence the agent SHOULD gather, what decision it SHOULD make, what action it SHOULD take, and how it SHOULD recover when evidence is incomplete.
```

### Body content

The Markdown body describes the behavior. It SHOULD be written for people and agents reviewing traces, designing evals, or aligning prompts. It is not primarily runtime prompt text.

A behavior is more than a low-level rule or one-off procedure. It describes how the agent gathers context, makes decisions, acts, and handles uncertainty.

A behavior body SHOULD:

- name a recurring behavior
- describe when the behavior applies
- describe desired conduct
- describe undesired conduct or failure modes

## Recommended behavior dimensions

Each behavior SHOULD make these dimensions clear. The Markdown format does not require specific section headings.

- **Intent:** why the behavior matters and when it applies.
- **Evidence:** what the agent SHOULD inspect, retrieve, preserve, or verify before deciding.
- **Decision:** what the agent SHOULD infer, choose, or become confident about.
- **Execution:** what the agent SHOULD do after deciding.
- **Recovery:** what the agent SHOULD do when the first path fails, evidence is incomplete, or the request is ambiguous.
- **Failure modes:** what bad or unintended behavior the spec is meant to prevent.

Omit a dimension if it would be trivial or redundant for a particular behavior.

A useful distinction: evidence is the input to a decision; decision is the conclusion; execution is the visible action; recovery is what happens when the first path fails.

### Explicit schema example

```markdown
# Behavior name

**Intent:** Why this behavior matters and when it applies.

**Evidence:** What the agent SHOULD inspect, retrieve, preserve, or verify before deciding.

**Decision:** What the agent SHOULD infer, choose, or become confident about.

**Execution:** What the agent SHOULD do after deciding.

**Recovery:** What the agent SHOULD do when the first path fails, evidence is incomplete, or the request is ambiguous.

**Failure modes:** What bad or unintended behavior this spec is meant to prevent.
```

## What belongs in a behavior spec

Add a behavior spec when the behavior is important across many interactions or traces.

Good candidates are behaviors that are:

- **Frequent**: they appear in a meaningful share of the agent's work.
- **High-impact**: mistakes affect correctness, trust, safety, cost, or user experience.
- **Agent-defining**: they capture a design choice about what kind of agent this is.
- **Ambiguous by default**: reasonable agents or prompt writers might behave differently unless the behavior is stated.
- **Spread across context**: a reviewer would otherwise need to read prompts, skills, tool docs, examples, traces, or evals to infer the behavior.
- **Useful for debugging**: naming the behavior helps explain failures in real traces.

Do not use behavior specs for every instruction the agent has received. Leave out rare low-risk details, tool syntax, one-off procedures, slogans, and eval implementation details unless they express an important behavioral commitment.

## Format versioning

This document defines format version `1`. Behavior specs MAY declare their format version with the optional `format_version` frontmatter field. If `format_version` is omitted, clients MUST treat the behavior spec as format version `1`.

Clients MUST ignore unknown frontmatter fields for supported format versions. Future format versions SHOULD preserve backward compatibility where possible. Clients that encounter an unsupported `format_version` SHOULD skip the behavior spec and surface a diagnostic.

## Optional directories

### `references/`

Supporting material for reviewers or eval authors:

- rationale documents
- example traces
- background docs
- domain-specific context

## Discovery and use

Tools that support Agent Behavior SHOULD discover behavior specs by scanning `.agents/behaviors/` for subdirectories containing `BEHAVIOR.md` or a supported case variant.

At minimum, a discovered behavior record contains:

| Field | Description |
| --- | --- |
| `name` | Stable behavior identifier from frontmatter |
| `description` | Short description from frontmatter |
| `location` | Absolute or project-relative path to `BEHAVIOR.md` |

Unlike [skills](https://agentskills.io/home), behaviors are not primarily loaded to help the model complete the next task. Clients SHOULD not automatically inject all behavior specs into runtime prompts unless they are intentionally building a behavior-conditioned agent.

Behavior specs are usually loaded when:

- reviewing traces
- designing or updating evals
- auditing prompts, skills, or tools
- debugging behavior regressions
- generating documentation about expected agent conduct

## Validation

Validation has two layers: structural validity, which tools can check mechanically, and quality, which requires human or model judgment.

### Structural validity

A structurally valid behavior directory:

- is a directory under `.agents/behaviors/`
- contains `BEHAVIOR.md` or a client-supported case variant
- has YAML frontmatter delimited by `---`
- has frontmatter that parses as a YAML mapping
- includes a non-empty `name` field
- uses a `name` that is at most 64 characters
- uses a `name` containing only lowercase letters, numbers, and hyphens
- uses a `name` that does not start or end with a hyphen
- uses a `name` that matches the parent directory
- includes a non-empty `description` field
- uses a `description` that is at most 1024 characters
- if present, uses `format_version` as a positive integer
- if present, uses `metadata` as a key-value mapping

Clients SHOULD skip structurally invalid behavior specs and surface a diagnostic rather than loading a partial or ambiguous spec.

### Quality criteria

A useful behavior spec SHOULD:

- name a recurring behavior
- describe when the behavior applies
- describe desired conduct
- describe undesired conduct or failure modes
- make clear what evidence the agent SHOULD gather, what decision it SHOULD make, what action it SHOULD take, and how it SHOULD recover when evidence is incomplete
